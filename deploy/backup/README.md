# PostgreSQL → свой S3

Отдельная задача Railway создаёт архив PostgreSQL 18 (`pg_dump --format=custom`),
проверяет его каталог и выгружает в приватный S3-совместимый бакет.
Контейнер завершается после выполнения и не расходует CPU между запусками.

Настроено 8 ноября 2026: Yandex Object Storage, бакет `baza-backup`,
префикс `baselounge/postgres/`. Первый запуск в 19:52 МСК завершился успешно:
созданы все три периода, проверены скачанный архив и его каталог.

[Запуски и управление в Railway](https://railway.com/project/00fe363a-272e-4bf9-bfb7-b3e842174b3d/service/725d1d3c-d8cf-487d-a080-f020b9e5b39d/schedule?environmentId=3ce54703-376f-4683-822d-f4551dcdf65e).

## Настройки Railway

- Отдельный сервис `postgres-backup`, тот же проект и регион, что и `Postgres`.
- Root Directory: `/deploy/backup`, Dockerfile: `Dockerfile`.
- Cron Schedule: `0 0 * * *` — ежедневно в **03:00 по Москве**.
- Restart Policy: `NEVER`; одна реплика; публичный домен и volume не нужны.
- Команда запуска берётся из `ENTRYPOINT` образа.

| Переменная | Значение |
|---|---|
| `DATABASE_URL` | `${{Postgres.DATABASE_URL}}` |
| `S3_BUCKET` | Имя существующего бакета, без `s3://` |
| `S3_ENDPOINT` | HTTPS endpoint провайдера; для AWS S3 можно не задавать |
| `S3_REGION` | Регион провайдера, по умолчанию `us-east-1` |
| `S3_PREFIX` | Отдельный префикс, по умолчанию `baselounge/postgres/` |
| `S3_ADDRESSING_STYLE` | `path` по умолчанию; `virtual` для virtual-host addressing |
| `AWS_ACCESS_KEY_ID` | Ключ доступа, только в переменных Railway |
| `AWS_SECRET_ACCESS_KEY` | Секретный ключ, только в переменных Railway |

Не записывайте ключи в Git или Dockerfile. Ключу нужны `ListBucket` для выделенного
префикса и `PutObject`, `GetObject`, `DeleteObject` для объектов внутри него.
Никакие права на другие папки бакета задаче не нужны.

## Хранение и проверка

В выделенном префиксе создаются папки `daily/`, `weekly/` и `monthly/`:

- ежедневные копии хранятся 6 дней;
- недельные создаются в воскресенье и хранятся 27 дней;
- месячные создаются первого числа и хранятся 89 дней.

При первом запуске создаётся начальная копия для каждого периода.
Перед очисткой задача сверяет размер и SHA-256 загрузок, скачивает дневной архив
обратно, проверяет его SHA-256 и каталог `pg_restore --list`.
Это проверка целостности, а не полноценное пробное восстановление базы.

Очистка затрагивает только файлы этой задачи с ожидаемым именем внутри указанного
префикса. Для каждого периода всегда остаётся хотя бы одна копия.
Если выгрузка или проверка завершается ошибкой, очистка не запускается.

## Восстановление

Скачайте выбранный `.dump` и восстановите его **в отдельную новую PostgreSQL 18**:
задайте `PGHOST`, `PGPORT`, `PGUSER` и `PGDATABASE` новой базы в окружении.
Пароль будет запрошен интерактивно.

```sh
pg_restore --dbname="$PGDATABASE" --password --no-owner --no-acl --exit-on-error backup.dump
```

Сверьте данные до переключения приложения на восстановленную базу.
Архив содержит все таблицы приложения, в том числе аватары и историю миграций.
Роли PostgreSQL и настройки сервера в архив не входят.
